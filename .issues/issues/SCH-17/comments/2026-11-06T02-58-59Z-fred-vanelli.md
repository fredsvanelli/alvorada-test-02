### Why `runbooks-playwright` stayed down while the headed server reconnected

Claude Code never retried `runbooks-playwright` after `.env.local` existed. The headless mode itself works.

| Time (UTC, 2026-11-06) | Event |
|---|---|
| 01:37:15 to 01:37:17 | `/mcp` tries `runbooks-playwright`, which fails with `ENOENT` on `.env.local`. This is its last logged connection attempt. |
| 01:37:26 and 01:37:48 | `/mcp` tries `runbooks-playwright-headed` twice, and both fail with `ENOENT`. |
| 01:39:53 | The root `.env.local` is created. |
| 01:41:51 | `/mcp` retries only the headed server, which connects. |

Evidence:

- The MCP logs in `~/.cache/claude-cli-nodejs/` and the transcript of session `851c740b` show the attempts above. The transcript's `/mcp` output after the file existed names only the headed server.
- Claude Code did not retry the failed server on its own in the hour after that, and `/clear` kept the same process (PID 84080). New sessions in that process kept reporting the 01:37 failure as `CONNECTION_CLOSED`.
- Started directly with the empty file in place, both servers answered `initialize`.

SCH-17 removes the cause of the crash by dropping `--secrets` from `.mcp.json`. A server that has already failed in a running Claude Code process still needs its own `/mcp` reconnect or a new process.
