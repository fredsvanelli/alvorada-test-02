## Implementation plan

Design: `docs/superpowers/specs/2026-11-05-sch-8-cancel-and-list-design.md`. Plan: `docs/superpowers/plans/2026-11-05-sch-8-cancel-and-list.md`. ADR: `docs/adr/0001-nested-resource-in-booking-responses.md`.

Decisions from the grill session:
- Cancel answers 200 `{ result: "canceled" | "already_canceled", booking }`, and 404 `{ error: "not_found", message }` for an unknown id or one that can't exist (fails the id pattern, no database call).
- `GET /bookings`: no filters, bare array, ascending id order by character code.
- Every booking response (list, create, cancel) nests `resource: { id, name }`; requests still send the resource id. This changes create's 201 body (SCH-6 contract), done here.
- The resource name comes from a SQL `JOIN` in `BookingsRepository`.

Tasks:
1. Nest the resource in the create response (OpenAPI, `bookings.create-booking` runbook).
2. `GET /bookings` + runbook `bookings.list-bookings`.
3. `POST /bookings/:id/cancel` + runbook `bookings.cancel-booking`, including the SCH-6 note: a canceled booking never conflicts, and its id still returns `id_taken`.
4. Two steps on `bookings.check-availability` from the SCH-7 note: a check writes nothing, a canceled booking no longer conflicts.
5. test, lint, typecheck, build, affected runbooks, `/utils:review-work`.
