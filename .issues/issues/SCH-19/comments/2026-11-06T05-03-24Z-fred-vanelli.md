## Implementation plan

Agreed in a grill-with-docs session: one page-level `logged()` wrapper records each call when its reply arrives; page load and Retry log `GET /resources` then `GET /bookings` once both answer; every sent availability check is logged; GETs are green on 2xx, red otherwise; POSTs keep their result-card tone; bodies print as indented JSON (status on its own line); the panel caps at 640px with only the list scrolling (focusable, no auto-scroll); 30 entries kept; a `useRef` guard stops StrictMode from loading twice in dev.

1. **Log helpers** (`web/src/lib/bookings.ts`, tests first): `LOG_SIZE` 30; `LogEntry.request` (pretty request body); `describeCall` returns the path line; `describeBody` pretty-prints; `describeReply` gives `status` + newline + pretty JSON or raw text, network failure stays one line; `getTone` (2xx ok, else error).
2. **Page wiring** (`bookings-page.tsx`): `record`/`logged`; `fetchAll(record)` logs in fixed order; `write()` logs the POST with the card tone and the re-fetch; the preview effect logs each check; `useRef` load guard.
3. **Panel** (`operation-log.tsx`): `max-h-[640px]`, scrolling `<ol>` with `tabIndex={0}`, `whitespace-pre-wrap` request (white) and reply (tone) blocks.
4. **Runbooks + scripts** (`/runbooks:update`): view-home (load entries, red failed load, Retry entries, new 640px/scroll step), preview-availability (`GET /availability` entries), book-from-form and cancel-from-table (re-fetch entry above the POST, no-POST steps, cap note 30). Runbooks use exact numbers only for page load.
5. **Checks**: test, lint, typecheck, build, test:e2e, `/runbooks:run --affected`, `/utils:review-work` before the PR.
