## Implementation plan

Agreed in the design session:

- `validInterval` is renamed `parseInterval(start: unknown, end: unknown): Interval | null`. It returns the parsed numbers, or `null`, which callers map to `invalid_data`.
- Each value is a number, or a digit-only string (`/^\d+$/`) converted with `Number()`. Anything else is rejected, so `""`, `" 10 "`, `"1e3"`, `"0x10"`, `"10.0"`, `"+10"` and `"-5"` return `null`.
- Times are integers in `0..2147483647`: negatives are invalid, and the upper bound is Postgres `integer`. `start < end`.
- `overlaps(a, b)` is `a.start < b.end && b.start < a.end` and doesn't validate its inputs.
- `type Interval = { start: number; end: number }` is exported and shared with the service and entity (SCH-6).

Steps:

1. Docs: `CLAUDE.md` and `docs/diagrams/architecture.md` say `parseInterval`. `GLOSSARY.md` says Interval times are non-negative.
2. Tests first in `api/src/bookings/booking-rules.spec.ts`: accepted and rejected tables for `parseInterval`, plus `overlaps` cases for touching, one-unit overlap, containment, identical and disjoint intervals, each in both argument orders.
3. Implement `api/src/bookings/booking-rules.ts` with no Nest or TypeORM imports. Test, lint, typecheck and build must pass.
4. Update the SCH-5, SCH-6 and SCH-7 texts to the new name. SCH-7 no longer parses the query string itself.
5. Run `/utils:review-work` before the PR.
