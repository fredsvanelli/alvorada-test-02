Two deliberate departures from this issue, agreed during design (`docs/superpowers/specs/2026-11-05-sch-10-web-ui-design.md`, "Departures from the issue"):

1. **No Check button.** The scope lists "Book and Check". Instead, a live preview line under the form calls `GET /availability` while you type (about 250 ms debounce, latest answer wins). It shows "R1 [19,21) is available" or "R1 [19,21) conflicts with A, B" (ids in API order) and draws a dashed box on the timeline. It creates nothing. This is how acceptance criterion 3 is met.
2. **The UI can't cancel a booking twice.** A canceled row's Action cell is empty, and there is no cancel-by-id. So the second half of criterion 4 ("canceling it again shows `already_canceled`") can't be reached from the page; only a stale row (canceled from another tab or by curl) could trigger it. The UI still maps `already_canceled` to its result card (unit test in `web/src/lib/bookings.test.ts`), and the `bookings.cancel-booking` api runbook proves the API behavior.
